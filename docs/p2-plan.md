## P2-1 正文编辑器 + 改稿 diff　✅ 已交付（2026-09-20）

> 交付说明见 `docs/editor.md`。以下为立项时的依据，保留备查。

**依据（实测）**
- `console.html` 里 9 个 `textarea` 全部是 JSON / 配置 / 粘贴用途（Agent 输入、卡密、插件代码、
  GEO 查询、模板描述…）——**没有一个是编辑正文的**。
- 阅读器 `openReader()` 25 处调用，**全部只读**。
- 前端 `diff` 字样出现 **0 次**。

**这意味着什么**
AI 出了一篇稿，人只能「通过」或「打回重跑」。**想改一个词都得回 Sanity 后台或者重跑一次 Loop。**
而内容团队真实工作里最高频的动作恰恰是「改两句就能发」。这一条不补，
「在 MFlow 里做内容」就永远停在「看 MFlow 生成的内容」。

**做什么**
1. 阅读器加「编辑」态：markdown 编辑区 + 右侧实时预览（复用已有 md 渲染）。
2. 保存 = **重跑四道门禁**（quota / lang / anti-slop / post-write），BLOCK 就不让存为「可发布」。
3. 本地稿留版本：`run/projects/{id}/versions/{slug}/{ts}.md`，最多留 10 版。
4. 改稿类任务（`rewrite` / `landing_refresh` / QA 修复）产出页加**左右 diff**，逐段高亮。
5. Sanity patch 前的确认弹层直接展示 diff（`audit-changes.jsonl` 已存 before/after，只差渲染）。

**成本**：中（前端为主，门禁与版本后端已有）
**验收**：能在后台改一个词 → 重新质检通过 → 走已有授权流发布；改稿任务能一眼看出改了哪几段。

## P2-2 Agent 流式输出　🔴

**依据（实测）**：前端 `EventSource` / `stream(` 出现 **0 次**。Agent 对话是请求—等待—整段返回。

**这意味着什么**
多步规划或长文生成时，用户对着转圈等几十秒到几分钟，**中途无法判断有没有跑偏**，
只能等它跑完再决定要不要推翻。这也是「长文 skill 流程（7500 词级）」迟迟接不进来的真正原因——
接进来体验也不可用。

**做什么**
- `/api/agent/chat` 增 SSE 流式（**服务端 SSE 基建已有**：`_send_sse_mcp` + `/api/mcp/sse`，直接复用）。
- 流式推三种事件：`token`（增量文本）、`tool`（正在调哪个工具）、`step`（规划到第几步）。
- 前端加「停止生成」按钮——能中断，才敢让它跑长任务。

**成本**：中低（后端有现成 SSE，前端一个 EventSource）
**验收**：Agent 回复逐字出现；工具调用实时可见；可随时中断。

## P2-3 内容库索引化（顺带解掉 T2 增量同步）　🟠

**依据（实测）**
```python
def library_list(site, section, lang="", q="", limit=200):
    for f in sorted(base.rglob("*.md")):   # ← 每次请求全扫 17,535 个文件再截 200
```

**这意味着什么**
内容库、搜索、多语言覆盖、QA 范围展开、内链体检、物料扫描——**全都建在这个函数上**。
规模每涨一倍，这六个功能一起变慢。P1-4 内链那次「20 项卡住 → <8s」已经是被这个问题咬过一次，
当时的解法是给内链单独加索引，**根因没动**。

**做什么**
1. `run/library/{site}/index.json`：path / title / lang / section / slug / mtime / hash。
2. 同步时按 `_updatedAt` 增量更新索引（= T2 增量同步的一半工作）。
3. `library_list` 改走索引 + 真分页（offset/limit），搜索走索引字段。
4. 内链那套私有索引并回统一索引。

**成本**：中　**验收**：内容库列表 <200ms；`--sync-library` 从全量 3 分钟降到增量数秒。

## P2-4 每日体检推送（让人不用主动打开后台）　🟠

**依据**：Loop 终态已推飞书（P5.4），但**系统整体状态没有任何主动推送**。
`warmup.py` / `/api/health` / `/api/inbox` 的信息只有打开浏览器才看得到。

**这意味着什么**
「每天用起来」的前提不是后台多好用，而是**它会主动找你**。
否则忙起来三天不打开，熔断了、配额满了、剧本停了都不知道。

**做什么**
- 每日 09:00 一条飞书卡片：健康等级 · 昨日产出（生成/发布/修复数）· 待办（收件箱 N 条）·
  异常（熔断/失败任务/配额告警）· 一句话建议。
- 内容复用 `health` + `inbox` + `overview`，**不新造数据源**。
- 周一那条加一周汇总（吞吐 / BLOCK 率 / token 成本 / GEO 提及率环比）。

**成本**：低（数据全有，就是组装 + 一个 systemd timer）
**验收**：不打开后台也知道系统昨天干了什么、今天该管什么。

## P2-5 单位成本可见　🟠

**依据**：有 `usage` 页和 token 记账（按用户/月），**但没有「这篇文章花了多少钱」**。

**这意味着什么**
内容工厂的核心经营指标是**单篇成本**和**单篇 ROI**。现在能回答「这个月花了多少 token」，
回答不了「一篇 blog 平均 X 元，落地页 Y 元，改稿比新写省多少」——
而这才是决定「要不要放量」的那个数。

**做什么**
- 批量任务 / Loop 记账时把 token 摊到条目级，落 `run/cost.jsonl`（item / type / tokens / 估算金额）。
- 自我迭代仪表加第五条曲线：**单篇成本趋势**（按 blog / landing / rewrite 分类）。
- 内容库条目详情显示「生产成本」；配合 impact 可算单页 ROI。

**成本**：低中　**验收**：能回答「改稿比新写便宜多少」。

## P2-6 剧本版本与回滚　🟡

**依据**：剧本编辑器很好用，但 `playbook_save` 直接覆盖——**改错了退不回去**。
而变更审计（`audit-changes.jsonl` + 字段级回滚）的模式已经现成。

**做什么**：`playbooks.json` 存最近 5 版；编辑器加「历史版本 / 恢复」；改动进 `audit-changes.jsonl`。
**成本**：低　**验收**：改坏一个剧本能一键退回上一版。

## P2-7 console.py 拆分（先补测试，再动刀）　🟡

**依据**：`console.py` **10,490 行**，`console.html` 3,606 行。近 6 天几乎每次提交都改 console.py。
42 个单测只覆盖纯逻辑函数（spec_guard / 熔断 / 配额 / 预设 / 剧本分支），
**HTTP 层、执行器、存储层无测试**。

**这意味着什么**
不是「代码不好看」的问题——是**改动风险在涨**。P7-C 那道语法门禁就是被 4 次语法回归逼出来的；
门禁能挡语法错，挡不住逻辑回归。

**做什么（顺序不能反）**
1. 先补执行器与存储层的单测（batch_create / run_tick / playbook_run 的状态迁移）。
2. 再抽两层：`storage.py`（读写/原子写/锁）、`executors.py`（6 类执行器）。
3. HTTP 路由保留在 console.py，只做分发。

**成本**：高（但可分次）　**验收**：改执行器不再需要通读万行文件；单测覆盖三个核心状态机。

## P2-8 导航信息架构：31 项 vs「0 门槛」　🟡

**依据（实测）**：`NAV_GROUPS` 共 **31 个导航项** / 6 组。而产品原则第 3 条是
「每个新能力必须让未配置的新用户 5 分钟内看到效果」。

**这意味着什么**
31 项对天天用的人是效率，对第一天上手的人是劝退。已有的开工向导解决了「第一次配什么」，
没解决「平时看哪几页」。

**做什么**
- 按已有的**三模式**收敛默认可见项：Pipeline 模式露 8 项，Flow 露 14 项，Loop 露全部。
- 「更多」折叠其余；命令面板 ⌘K 已经能直达，不怕藏。
- 手机端只保留**收件箱 + 审批 + 健康**三项——审批这种动作最适合在手机上完成。

**成本**：低　**验收**：新用户默认看到 8 项；老用户一键展开全部。

## P2-10 库 → GEO 闭环联动（T8）　🟡

**依据**：GEO 缺口能一键「→ 选题队列」或「→ 改稿 Loop」，但**判断「该新写还是该改稿」靠人**。
内容库索引（P2-3）做完后，这个判断可以自动化。

**做什么**：缺口查询 × 库内语义检索（RAG 已有）→ 命中且相关度高 → 改稿；无命中 → 新写。
**成本**：低（依赖 P2-3 + 已有 RAG）　**验收**：0 引用查询能自动分流到改稿/新写两条队列。

## 明确不做

- 不引入前端构建链（React/Vite）。单文件 HTML 是这个项目「文件即状态」的一致选择，
  换框架的收益换不回迁移成本和新的运维面。需要的是**拆函数**，不是换技术栈。
- 不为 P2-7 做大爆炸式重构。先测试后拆分，分次落地，每次可回滚。
- 不新增数据库。规模触发信号仍是「语料 > 10 万块」或「多租户隔离」，现在都没到。
