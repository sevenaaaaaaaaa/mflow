# lovart-kb-mine — KB 查询 / grounding

> **位置**：1-2 Insight/Knowledge Base/ 是 content generation 的真源头。
> Writer 在写 brand / product / capability 内容前必须先 call 此 skill，否则会写出「后生成无价值」内容。

---

## When this skill loads

加载条件（满足任一即触发）：

- writer profile（lovart-creation / lovart-page-serp-writer / lovart-blog-signal-writer 等）启动
- 用户说 "查 KB"、"mine KB"、"KB 给这段 topic 哪些 unit"
- 内容涉及 Lovart 产品 / 品牌 / capability（如 "ChatCanvas"、"Brand Kit"、"Sora 2" 等）
- 拓关键词时需要「能力映射」

不加载：

- 与 Lovart 产品无关的内容（如 ORM 报告 / 网站技术 SEO）
- KB 完全空白的 topic（先入库再写）

---

## Process (调用顺序)

```
1. 解析用户/上下文给的 topic + capability hint
2. bash 1-2 Insight/Knowledge Base/scripts/kb-mine.py \\
      --root <vault> \\
      --topic "<topic>" \\
      [--capability-mode] \\
      [--json]
3. 拿到 JSON 结果{matched_topics, topic_hits, capability_hits, verbatim_quotes}
4. 在 brief 中拼 KB context：
   - topic_hits (top 3) → 摘要 + source_urls
   - capability_hits (各 cap) → canonical_url + 关联 units
   - verbatim_quotes (≤3) → 可直接用于 "Lovart 官方说... [kb-xxx]"
5. (建议)：
   - 把 KB canonical_url 当 shortlist，writer 引 URL **只**用此清单
   - 复核 capability 名是否在 glossary，是 → safe；否 → 警告不可铸 brand new capability
6. 进 dispatch → hermes/opencode writer，prompt 含上述 context
7. writer 输出后 → 此 KB context 在 quality cascade MUST-CITE-KB 检查里验证
```

> ⚠️ 不要在 brief 里塞 verbatim quotes 全段（太长会触发 token budget）；改成 "KB context: ...[摘录]"

---

## Output format

返回时一律给一个紧凑 KB context block（markdown）：

```markdown
## KB context (from lovart-kb-mine)

### matched topic hits (top 3)
- [auth=4] kb-{slug} ({origin}) — {snippet}
  - URLs: https://...
- [auth=3] kb-{slug} (internal-curated) — {snippet}

### capability hits (top 5)
- ChatCanvas → canonical_url https://www.lovart.ai/docs/agent/upload-files (10 units)
- Brand Kit → canonical_url https://www.lovart.ai/news/LA-Tech-Week-Event-Blog (9 units)
- ...

### verbatim quotes (≤3, use with citation marker)
- "[kb-{slug}] direct quote ≤120 chars"

### hard constraints (writer must comply)
- URLs above are the **only** allowed URLs in the published draft.
- Capability names above are the **only** Lovart-feature terms allowed.
- Citation marker format: `[kb-{slug}-{n}]` — must flow through to body text.
```

---

## Hard rules

1. **MUST QUERY FIRST**：writer profile 启动时第一动作 = `kb-mine --topic`。
2. **URL 列表 shortlist**：仅引用 KB 出来的 canonical_url；其他 URL 视为 BLOCK-on-cite。
3. **Capability 只用 KB 内名字**：「ChatCanvas」**不**写「Canvas」/「chat canvas」/「Cavnas」（拼写漂移必检）。
4. **不 cache 跨 run**：每次 write 重新 mine；KB 内容变 → context 变。
5. **不擅改 KB**：need new entry 时走 skill `lovart-kb-ingest` (URL list)；不直接编辑 .md。
6. **不阻塞**：如果 KB 命中是空，writer 仍继续，但要带 WARN 到 quality cascade（Phase 3 接 KB density WARN）。

---

## Boundary with other skills

| 同级 skill | 与 mine 关系 |
|-----------|-------------|
| `lovart-blog-signal-writer` | 上游：brief → mine → writer dispatch |
| `lovart-page-serp-writer` | 同上 |
| `lovart-content-quality-gates` | **下游**：用 KB 索引做 MUST-CITE-KB 验证 |
| `lovart-kb-ingest` | **横向**：KB 没命中时调用，扩张 KB |
| `lovart-quality-cascade` | **横向**：cascade 内每个 iter 重 mine（不传 KB context over iters） |

---

## Failure modes (NEVER)

- 「writer 不调 KB」→ writer 是后生成无价值主因，**强制** mine-first。
- 「KB context 写进 draft 里」→ context 是 brief 元数据，**不**进 draft。
- 「KB 写入后 draft 不引用」→ MUST-CITE-KB 必 BLOCK 在 cascade。
- 「URL 不在 KB」→ BLOCK-on-cite 立即拒。
