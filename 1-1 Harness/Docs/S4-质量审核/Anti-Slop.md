# Anti-slop 内容写作规范

这份规范用于约束 Lovart 的对外内容：落地页、Blog、产品文案、SEO 页面以及多语言版本。目标不是把文字写得更“像人”，而是让每一段内容承担明确任务：让读者更快理解、更愿意相信、更知道下一步该做什么。

“Anti-slop”不是反对 AI 辅助写作，而是反对无对象、无判断、无证据、无转化、无上下文的内容垃圾。

## 1. 总原则

### 1.1 什么是 AI 泔水

以下情况一律视为低质量内容：

- 没有读者：不知道这段话写给设计师、增长负责人、电商卖家、创始人，还是普通创作者。
- 没有任务：标题不引导点击，描述不解释价值，CTA 不推动下一步，段落不服务上下文。
- 没有信息差：整段只是在说“提升效率、释放潜力、开启未来、无缝体验”。
- 没有证据：使用“行业领先、革命性、10x、企业级、全链路”但没有场景、机制、数据或案例支撑。
- 没有语气控制：英语、简体中文、日语等主要语种都写成同一种冷冰冰的机器口吻。
- 没有节奏：所有句子长度相近，所有段落结构相同，所有小标题都像模板变量。
- 没有取舍：为了 SEO 把关键词塞满页面，为了显得专业堆术语，为了显得亲切过度口水化。

### 1.2 好内容的基本判断

一段内容发布前，至少要回答四个问题：

1. **谁会读**：读者处于什么角色、能力水平、决策阶段和情绪状态。
2. **为什么现在读**：他是从搜索、广告、社媒、产品内入口还是邮件进来，带着什么问题。
3. **读完改变什么**：他获得了一个判断、一套方法、一个新视角，还是一个明确行动理由。
4. **下一步是什么**：继续阅读、试用、比较、收藏、分享、购买，还是回到产品完成某个动作。

### 1.3 语言边界

内容要专业，但不能把专业感误解为名词密度。内容要像人说话，但不能把人话误解为随便、贫乏、过度口语。

- 英文：少用抽象营销套话，多用具体动作、对象、结果和权衡。
- 简体中文：避免“赋能、闭环、抓手、链路、生态位”这类无必要黑话；需要时可以用，但必须说明它在这里具体指什么。
- 日语：避免直译中文结构；优先使用自然的敬体或品牌语气，不把每句都写成硬邦邦的功能说明。
- 多语言版本不是逐句翻译，而是同一策略在不同语言中的重写。SEO 关键词可本地化，用户痛点也要本地化。

## 2. 落地页

落地页的质量不由“文案漂亮”决定，而由每个模块是否推动转化决定。每一屏都要回答一个递进问题：我为什么停下、为什么相信、为什么现在行动。

一张合格落地页的最低标准是：用户不用读完整页，也能在首屏知道产品是否与自己有关；读到中段时，能理解 Lovart 的差异不是一句形容词；读到结尾时，能找到符合当前顾虑的下一步。

### 2.1 创作前必须明确

- 页面类型：工具页、功能页、行业页、对比页、活动页，还是品牌介绍页。
- 流量来源：SEO、广告、社媒、联盟推荐、站内导流、邮件召回。
- 读者角色：个人创作者、设计团队、品牌方、电商卖家、代理商、产品经理等。
- 决策阶段：首次了解、正在比较、准备试用、付费前犹豫、已有需求但不信任 AI。
- 主要动作：免费试用、查看案例、生成一次、预约演示、阅读教程、对比方案。

### 2.2 模块原则

**Hero**要在首屏完成定位、痛点、差异和行动，不要只喊品牌愿景。

- 标题：说清楚“谁用它做什么、比原来好在哪里”。
- 副标题：补足机制和场景，而不是重复标题。
- CTA：动词要具体，降低风险或强调即时收益。
- 辅助文案：用于消除顾虑，例如无需信用卡、可商用、支持团队流程，但不能编造未经证实的信息。

**Problem / Use case**要写具体场景，不写抽象痛点。

- 差：Design faster with AI.
- 好：Turn a rough campaign idea into editable product visuals before the first creative review.

**Feature**要解释功能如何改变工作流，而不是罗列按钮。

- 功能名不是卖点，功能产生的判断、节省的步骤、减少的返工才是卖点。
- 涉及产品事实、价格、模型能力、兼容平台、用户数量时必须可溯源；无法确认时标注待确认，不得用猜测补齐。

**Proof**要优先使用可验证证据。

- 可用证据：案例、生成前后对比、用户引用、数据、工作流截图、公开来源、产品机制解释。
- 慎用证据：空泛 logo wall、没有出处的百分比、无法核验的“全球领先”。

**FAQ**不是填充 SEO 字数，而是处理转化阻力。

- 版权、商用、团队协作、导出质量、价格、学习成本、与现有工具关系，优先于泛泛的“什么是 AI 设计工具”。

### 2.3 SEO 与转化的关系

落地页可以服务 SEO，但不能为了关键词牺牲首屏判断。关键词应进入：

- title、H1、首段、核心模块标题、FAQ、meta description。
- 与搜索意图对应的比较段、教程段、场景段。
- 自然同义词和实体词，例如 design agent、AI design workflow、brand kit、product visuals。

不要把关键词塞进每个按钮。按钮是行动，不是关键词容器。

### 2.4 落地页自检

- [ ] 首屏是否能在 5 秒内说明页面给谁、解决什么、下一步做什么。
- [ ] 每个模块是否推进一个新判断，而不是重复“快、好、智能”。
- [ ] CTA 是否跟当前模块上下文一致。
- [ ] 是否有至少一个可信证据，而不是全靠形容词。
- [ ] FAQ 是否覆盖真实购买或试用阻力。
- [ ] SEO 关键词是否自然进入结构，而不是破坏阅读。
- [ ] 多语言版本是否按本地搜索意图重写，而非逐句直译。

## 3. Blog

Blog 不是“写长一点就专业”。Blog 的任务是让读者获得更高质量的判断：看完之后，他理解了一个问题的结构、看见了别人没讲清的关系，并知道自己下一步怎么做。

短小精悍可以成立，但只在信息密度足够高时成立。多数情况下，读者无法通过碎片阅读获得高认知，因此 Blog 应优先追求论证扎实、例子具体、观点有锋芒，而不是机械缩短。

一篇合格 Blog 的最低标准是：读者至少带走一个可复述的判断、一个可迁移的方法、一个具体例子，以及一个更好的问题。

### 3.1 写作前必须定义读者

每篇 Blog 开写前先写清楚：

- 读者是谁：初学者、专业设计师、增长负责人、电商运营、代理商老板、产品团队，还是 AI 工具研究者。
- 他为什么搜这个问题：找教程、做采购、比较工具、寻找灵感、解决卡点，还是验证某个趋势。
- 他已经知道什么：不要把高级读者当小白，也不要让初学者一上来吞术语。
- 他希望获得什么：步骤、框架、判断标准、案例、反例、工具清单、趋势解读，还是决策依据。
- 我们的专家定位是什么：设计专家、增长顾问、产品实践者、AI workflow builder，还是行业观察者。

### 3.2 文章结构

一篇合格 Blog 至少应包含以下层次：

1. **开场钩子**：指出读者真正关心的矛盾，而不是复述关键词定义。
2. **问题拆解**：把大问题拆成可理解的几个变量。
3. **核心观点**：给出明确判断，允许有立场，不要永远“取决于具体情况”。
4. **例子与反例**：用具体场景说明观点边界。
5. **方法或框架**：让读者能迁移到自己的工作里。
6. **视觉辅助**：用信息图、流程图、对比图或截图解释复杂关系。
7. **行动收束**：给读者一个下一步，不一定是强 CTA，也可以是检查清单或决策建议。

### 3.3 论据与旁征博引

旁征博引不是堆外链，也不是把文章写成资料汇编。引用、案例、类比和行业观察都要服务一个判断。

优先使用这些论据：

- 产品内真实工作流：例如从 brief、prompt、variation、review 到 export 的完整过程。
- 可验证行业事实：公开报告、搜索数据、产品文档、案例页面、发布说明。
- 对比性例子：传统设计流程、单次生成工具、可编辑设计代理之间的差异。
- 用户视角证据：真实抱怨、常见反对意见、采购问题、团队协作中的返工场景。
- 反例：说明某个方法在什么情况下会失败。

引用外部资料时，不要只把来源贴上去。必须解释“这条资料改变了什么判断”。如果引用不能改变判断，就删掉。

### 3.4 信息密度

Blog 要避免“看起来很多，读完没东西”。每个 H2 至少承担一种信息功能：

- 提供一个判断：例如“AI design tools fail when teams treat prompts as final assets.”
- 解释一个机制：例如“editable layers matter because review cycles are where most creative time disappears.”
- 给出一个可复用方法：例如三步评估工具是否适合品牌团队。
- 展示一个案例：例如电商主图、广告迭代、品牌活动视觉。
- 处理一个反对意见：例如“AI 生成图能不能商用”“会不会破坏品牌一致性”。

如果某个段落删掉后文章没有损失，它就不该存在。

### 3.5 标题与小标题

标题要同时服务点击、搜索和预期管理。

- H1：包含主关键词，但必须有明确承诺。
- H2：不要只写概念名，要写读者能获得的判断。好的 H2 本身就是一条微型结论。
- H3：用于组织步骤、案例、注意事项，不要把所有层级都写成“Benefits / Features / Conclusion”。

示例：

- 差：Benefits of AI Design Tools
- 好：Where AI Design Tools Actually Save Time: Briefs, Variations, and Review Loops

### 3.6 “加醋”的边界

“加醋”不是抖机灵，也不是把每段都写成段子。它指的是在合适位置加入人类作者的判断、比喻、现场感和轻微锋芒，让读者觉得这篇文章来自一个真的做过这件事的人。

可用方式：

- 在关键转折处点破行业常见误解。
- 用一个短例子替代三句抽象解释。
- 用一句有记忆点的话总结复杂判断。
- 把工具选择、流程选择背后的权衡讲出来。

不可用方式：

- 为了活泼牺牲准确性。
- 用网络梗替代论证。
- 把所有段落都写成夸张营销语。
- 用“毫无疑问、显然、革命性”掩盖证据不足。

### 3.7 多媒体与信息图

当文章解释流程、比较、决策、层级、前后变化时，应主动考虑信息图。

优先使用：

- 流程图：展示从 brief 到成稿、从 prompt 到 editable asset 的过程。
- 对比图：展示传统流程与 AI design agent 流程的差异。
- 决策矩阵：帮助读者选择工具、方案或工作流。
- 示例拆解图：标注一个好案例为什么有效。
- 截图或示意图：展示真实产品步骤，减少抽象描述。

不要为了“丰富”硬塞图片。每张图都要回答文字难以高效回答的问题。

### 3.8 Blog 自检

- [ ] 文章是否明确写给某类读者，而不是写给“所有人”。
- [ ] 开头是否提出真实矛盾，而不是百科式定义。
- [ ] 每个 H2 是否都有独立观点或方法价值。
- [ ] 是否至少有 2-3 个具体例子、反例或场景。
- [ ] 引用、案例或数据是否改变了文章判断，而不是装饰门面。
- [ ] 是否处理了读者最可能的怀疑。
- [ ] 是否有可视化机会，且图片/信息图承担解释任务。
- [ ] SEO 关键词是否融入标题、首段、H2、FAQ 和内链，而不是硬塞。
- [ ] 文章结尾是否给出清晰下一步，而不是“总之未来可期”。

## 4. 产品文案

产品文案服务的是用户正在做的动作。它必须清楚、可信、有边界，不能把界面变成营销海报。

一条合格产品文案的最低标准是：用户不需要猜当前发生了什么、不需要猜下一步在哪里，也不会因为文案过度承诺而误解功能边界。

### 4.1 原则

- 按用户任务写，不按内部功能名写。
- 先说结果，再补机制；必要时再解释限制。
- 错误提示要告诉用户如何修复，不只说“Something went wrong”。
- 空状态要给出下一步，而不是写欢迎词。
- 按钮使用动作动词，例如 Generate, Upload, Compare, Start from template。
- 涉及风险、权限、付费、删除、覆盖时，文案必须明确后果。

### 4.2 语气

产品文案可以温和，但不能啰嗦；可以专业，但不能居高临下。

- 差：Oops! Something magical went wrong.
- 好：The image could not be generated. Try a shorter prompt or upload a clearer reference.

### 4.3 产品文案自检

- [ ] 用户能否立刻知道当前状态。
- [ ] 用户能否知道下一步怎么做。
- [ ] 是否避免了内部术语外露。
- [ ] 是否在高风险动作前说明后果。
- [ ] 是否在错误、空状态、加载状态中保持一致语气。

## 5. SEO 页面

SEO 页面不是关键词容器。它是用户从搜索结果进入后，用最短路径判断“这个页面是否真的懂我的问题”的入口。

一张合格 SEO 页面的最低标准是：搜索用户能快速得到答案，搜索引擎能识别主题覆盖，业务能获得自然转化入口，三者不能互相牺牲。

### 5.1 创作前必须判断搜索意图

至少区分以下意图：

- 信息型：用户想理解概念、方法、趋势。
- 工具型：用户想找到能完成某件事的工具。
- 比较型：用户在比较品牌、功能、价格或替代方案。
- 交易型：用户接近试用或购买。
- 问题型：用户遇到具体卡点，想快速解决。

不同意图对应不同结构。不要用同一套模板写所有 SEO 页面。

### 5.2 页面结构

- 首屏回答搜索问题，避免长铺垫。
- 前 30% 提供核心答案、场景和判断标准。
- 中段覆盖相关实体、步骤、对比、FAQ、案例。
- 后段提供工具入口、内链、延伸阅读和转化动作。
- FAQ 回答真实长尾问题，不写为了凑 schema 的空问答。

### 5.3 SEO 页面自检

- [ ] title 和 H1 是否匹配搜索意图。
- [ ] meta description 是否说明具体价值，而不是泛泛欢迎。
- [ ] 首屏是否回答用户搜索的问题。
- [ ] 页面是否覆盖相关实体、同义词和上下文问题。
- [ ] 是否有内部链接连接到 Blog、Tools、Features 或 Pricing。
- [ ] 是否有自然 CTA，而不是突然推销。
- [ ] 是否避免关键词堆砌、重复段落和模板化 FAQ。

## 6. 语言本土化 skills

多语言内容不是把英文稿翻成各语种，而是为每个市场重新执行一次“读者、搜索意图、语气、证据、CTA”的判断。每个语言版本都要有自己的本土化 skill：它不只管语法，更要管用户预期、文化语感、搜索词、购买阻力和表达禁区。

### 6.1 通用本土化流程

每次生成或改写多语言内容时，按以下顺序执行：

1. **确认市场**：语言不等于市场。`en` 可能面向北美、全球 SaaS 或创作者社区；`pt` 可能面向巴西而不是葡萄牙。
2. **重查搜索意图**：同一产品词在不同语言里可能对应教程、免费工具、替代品、价格或案例。
3. **重写标题与首屏**：保留策略，不保留句式。H1、meta、Hero、CTA 必须按本地表达重写。
4. **替换例子**：行业、平台、工作流、节日、渠道、支付习惯和社媒平台应尽量贴近本地用户。
5. **校准语气**：判断该语言应更直接、更克制、更礼貌、更专家化，还是更具社区感。
6. **检查品牌术语**：Lovart、MCoT Engine、ChatCanvas、Touch Edit、Brand Kit 等核心术语保持一致；解释语可以本地化。
7. **做反直译检查**：删掉中文式英语、英文式日语、机器式简中，以及所有像“翻译腔”的长句。

### 6.2 语言 skill 表

| 语言 | 本土化 skill | 优先检查 |
|------|--------------|----------|
| `en` | 面向全球增长与 SaaS 读者，表达要清楚、具体、有判断，避免空泛营销腔。 | 是否用具体 workflow、role、outcome 替代 “unlock / empower / seamless”。 |
| `zh` | 面向简体中文用户，语气可以有锋芒，但不要变成互联网黑话或过度白话。 | 是否滥用“赋能、闭环、链路、抓手、生态”；是否有真实场景和判断。 |
| `zh-TW` | 不能把简中直接繁转；要使用台湾/繁中自然表达，避免大陆产品话术残留。 | 是否有简中词序、简中营销腔、用词不符合繁中读者习惯。 |
| `ja` | 日语要自然、克制、可信，少用直译长句；产品价值要通过场景和安心感展开。 | 是否像中文逐句翻译；敬体是否稳定；CTA 是否过硬或失礼。 |
| `ko` | 韩语要重视效率、趋势感和实际使用场景，但不能写成夸张广告体。 | 是否堆叠外来词；是否说明具体使用场景和结果。 |
| `de` | 德语读者更重视准确、边界、流程和可信度，避免未经证实的强承诺。 | 是否解释功能限制、数据来源、适用场景；是否过度夸张。 |
| `fr` | 法语内容要兼顾审美、品牌感和清晰结构，避免生硬英文句式移植。 | 是否自然表达设计语境；是否避免英语营销短语直译。 |
| `it` | 意大利语可以更有设计感和情绪，但仍要落到场景、流程和结果。 | 是否只有漂亮形容词；是否有具体创作场景。 |
| `pt` | 默认优先考虑巴西葡语市场，语气可更直接友好，但不能牺牲专业度。 | 是否使用巴西用户自然搜索词；是否避免欧洲葡语直译痕迹。 |
| `ru` | 俄语内容要直接、信息充分、逻辑清楚，少写空泛品牌愿景。 | 是否提供明确功能、步骤、边界和使用理由。 |

### 6.3 本土化质量门槛

- [ ] 每个语言版本都有本地化标题、描述、CTA，而不是共用英文结构。
- [ ] 每个语言版本至少检查 3 个本地搜索表达或同义实体。
- [ ] 示例、行业、平台、节日或用户场景至少有一处本地化调整。
- [ ] 品牌术语一致，但解释语按本地习惯重写。
- [ ] 不出现明显直译句式、混用语言、地区用词错位。
- [ ] 对高价值页面，必须由该语言的本土化 skill 单独审稿，而不是只跑通用检查清单。

## 7. 上下文限制防缩水机制

Agent 和大模型在长文、批量页面、多语言生成时容易因为上下文限制而缩水：前面写得细，后面变成提纲；Blog 原本需要论证，输出时被压成泛泛总结；多语言版本越到后面越像直译；落地页模块越多，越容易丢掉 CTA、FAQ、SEO 和证据。

这类缩水不是小问题。它会直接制造新的 AI 泔水。

### 7.1 禁止的缩水表现

- 后半篇明显比前半篇短，信息密度断崖下降。
- H2 只有标题，没有观点、例子、机制或反对意见。
- Blog 从“论证”缩水成“列表”，从“洞察”缩水成“建议”。
- 落地页只保留 Hero 和 Feature，丢失 Proof、FAQ、CTA、SEO 语义覆盖。
- 多语言批量生成时，后几个语言只做字面翻译，不再执行本土化判断。
- 结尾用“未来可期、总之很重要、开始你的旅程”草草收束。
- 因为上下文不够，擅自删除案例、引用、信息图 brief、检查清单或内链。

### 7.2 长内容分段生成规则

当内容超过单次稳定输出范围时，不允许一次性硬写完。必须拆成可校验的阶段：

1. **先定骨架**：列出 H1、H2、每节任务、目标字数、证据类型、图像/信息图位置。
2. **分段生成**：每次只写 1-3 个主要章节，保持每节达到同一质量门槛。
3. **维护内容 ledger**：记录已完成章节、未完成章节、每节是否含观点、例子、证据、CTA、SEO 词。
4. **续写前回读**：继续生成前先读上一段和骨架，不凭记忆续写。
5. **最后做完整性审计**：检查是否断尾、是否后半缩水、是否遗漏 FAQ/CTA/内链/图像 brief。

### 7.3 Blog 防缩水门槛

每个主要 H2 至少满足以下五项中的三项：

- 有一句明确判断。
- 有一个具体例子或反例。
- 有一个机制解释或方法步骤。
- 有一个读者可迁移的启发。
- 有一个与上下文自然衔接的下一步。

如果某个 H2 只剩 2-3 句概述，默认视为未完成，不得发布。

### 7.4 落地页防缩水门槛

落地页生成时，必须逐模块验收：

- Hero：定位、差异、CTA、风险消除。
- Problem / Use case：具体人群、具体场景、具体损耗。
- Feature：机制、结果、工作流变化。
- Proof：证据、案例、截图、引用或可验证事实。
- FAQ：真实阻力，不少于 3 个高意图问题。
- CTA：与页面阶段一致，不只复读主按钮。
- SEO：title、description、H1、H2、FAQ、内链和实体词覆盖。

缺一个模块不叫“精简”，叫未完成。

### 7.5 多语言批量防缩水

多语言内容必须按语言分批处理，不要一次生成所有语言并假装质量一致。

- 每批最多处理 2-3 个语言。
- 每个语言开始前重申该语言 skill。
- 每个语言结束后做本土化自检。
- 不得让后续语言复用前一语言的句式，只能复用策略。
- 如果上下文不足，优先保留读者定位、搜索意图、CTA 和事实边界，不能只保留漂亮句子。

### 7.6 完稿审计

发布前必须检查：

- [ ] 文档末尾完整，没有截断。
- [ ] 后 30% 的章节质量不低于前 30%。
- [ ] 每个主要章节都有观点、例子、机制或行动价值。
- [ ] 所有计划中的模块都存在，没有被“总结式压缩”吞掉。
- [ ] 多语言版本分别通过对应语言 skill 检查。
- [ ] 如果内容是分段生成，最终稿已统一标题层级、术语、CTA 和内链。

## 8. 反例与改写方向

### 8.1 落地页

差：

> Unlock your creative potential with an all-in-one AI platform that empowers teams to create stunning visuals faster than ever.

问题：没有对象、没有场景、没有机制，任何 AI 工具都能这么说。

改写方向：

> Turn campaign briefs into editable visual directions before your first review, so designers can compare ideas instead of rebuilding the same asset from scratch.

为什么更好：说明了场景、对象、工作流变化和具体收益。

### 8.2 Blog

差：

> AI design tools are changing the future of creativity. In this article, we will explore the benefits, features, and best practices of AI design.

问题：开头没有冲突，没有读者问题，也没有文章承诺。

改写方向：

> Most teams do not lose time because they lack ideas. They lose time when every idea has to be rebuilt, reviewed, revised, and rebuilt again. That is where AI design tools either become useful or become another toy.

为什么更好：指出真实矛盾，引出判断标准，给读者继续读的理由。

### 8.3 产品文案

差：

> Your request failed.

改写方向：

> We could not generate this image because the prompt is too long. Shorten it or remove conflicting style instructions, then try again.

为什么更好：说明原因和下一步。

### 8.4 SEO 页面

差：

> Our AI poster maker is the best AI poster maker for anyone who needs an AI poster maker online.

改写方向：

> Create poster concepts from a campaign idea, then refine layout, text, and visual style before exporting assets for review.

为什么更好：保留搜索意图，但把关键词落到实际任务。

### 8.5 缩水稿

差：

> AI design workflows can improve productivity. Teams should choose tools that fit their needs, create good prompts, and review outputs carefully.

问题：像结论，实际上没有结论；没有读者、场景、机制、例子，也没有下一步。

改写方向：

> If a design team still treats AI output as a flat final image, the review loop will not get shorter. The real gain starts when the first draft remains editable: the marketer can compare campaign angles, the designer can adjust layout without rebuilding, and the creative lead can reject a direction without throwing away the entire asset.

为什么更好：指出失败条件，解释机制，并展示团队协作场景。

## 9. 发布前总检查清单

### 9.1 内容策略

- [ ] 读者角色明确。
- [ ] 页面任务明确。
- [ ] 主要搜索意图明确。
- [ ] 转化动作明确。
- [ ] 关键事实有来源或标注待确认。

### 9.2 文案质量

- [ ] 标题承担点击、理解或判断任务。
- [ ] 描述补充具体场景或机制。
- [ ] CTA 与上下文一致。
- [ ] 没有大面积空话、套话、堆词。
- [ ] 专业词出现时有解释、例子或上下文。
- [ ] 语气符合页面类型和读者状态。

### 9.3 SEO 与结构

- [ ] 主关键词自然出现在 title、H1、首段和至少一个 H2。
- [ ] 相关实体、同义词、长尾问题被自然覆盖。
- [ ] 内链指向真实可用页面。
- [ ] FAQ 回答真实问题。
- [ ] 结构便于浏览，不让读者在大段文字里找答案。

### 9.4 多语言

- [ ] 不是逐句直译。
- [ ] 本地搜索词、语序、礼貌程度和行业表达自然。
- [ ] 品牌术语一致。
- [ ] 没有中文结构污染英文或日语。
- [ ] 简体中文、繁体中文、日语等版本没有混用表达。
- [ ] 已按目标语言调用对应本土化 skill，而不是只跑通用翻译检查。

### 9.5 防缩水

- [ ] 长内容已拆段生成并做完整性审计。
- [ ] 后半部分没有明显短于、薄于前半部分。
- [ ] Blog 每个主要 H2 至少包含判断、例子、机制、启发中的三项。
- [ ] 落地页没有遗漏 Proof、FAQ、CTA、SEO 等关键模块。
- [ ] 多语言批量内容没有越到后面越直译、越短、越空。

## 10. 最后一条硬规则

如果一段文案只能让人感觉“这个品牌很会说漂亮话”，但不能让人更理解、更相信、更想行动，就删掉重写。
